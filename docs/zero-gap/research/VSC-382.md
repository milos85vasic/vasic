## Defect class

Build-if-missing: a helper binary is built only when `[ ! -x BIN ]`, so once any binary exists, source edits are
never picked up and a gate or deploy step runs a stale tool. The register item cites three sites
(`scripts/verify-workable-items.sh` two legs and `_tools/deploy-langs.sh` site-build). The class is detected by
`scripts/zero-gap-class-build-if-missing.sh`.

## Alternatives considered

1. Always run `go build -o BIN` (the register's first suggestion): simplest and cache-cheap, but adds a build to
   every gate run and fails the gate when the toolchain is absent even though a usable binary exists.
2. A shared helper under `scripts/lib`: removes duplication but changes three call sites plus a new file; larger
   blast radius than the defect needs.
3. Rebuild when any `*.go` source under the tool tree is newer than the binary (chosen): keeps the fast path,
   closes the staleness hole, and is a local edit at each site.

## Why the fix is right

The staleness condition is exactly "a source file is newer than the binary", and the guard tests that condition
with `find -newer`. The closure check runs the detector against the real cited files in a scratch corpus and is
RED at the pre-fix ref and GREEN on the working tree, so it asserts the real condition rather than file presence.
Residual limit: mtime comparison can miss a source edit that preserves an older mtime (for example a checkout that
restores timestamps); content hashing would close that and was not adopted.
