# CV / Cover-Letter Design and ATS Parsing Reality — Research Digest

**Date:** 2026-11-19
**Purpose:** Input for a CV + cover-letter generation engine (LaTeX/PDF, DOCX, HTML) targeting a senior software engineer (17 years, AI/LLM + mobile).
**Method:** Five rounds of web research (visual design, ATS parsing, LaTeX mechanics, cover letters, measurement), plus direct reads of the two strongest primary studies found (ATSPrep's 108-document synthetic extraction corpus; latexci's 15-document LaTeX extraction bench).
**Rule applied throughout:** every number below carries the URL it came from. Where a figure is vendor-published, opinion-survey, or unreplicated, it is labelled. Anything not established is marked UNVERIFIED.

## Round A — Modern CV visual design, 2026

### FINDINGS

- **The type scale is stable across every serious source.** Body 10–12 pt, section headers 12–16 pt, name 18–24 pt bold, job titles 11.5–12.5 pt. 8 pt is rejected on two grounds simultaneously: hard to read *and* measurably more likely to be misparsed. — https://www.infiniteresume.com/blog/resume-formatting-standards-guide
- **Spacing values from a shipped template system** (these are production defaults, not theory): 12–16 pt before a section header (14 pt), 4–6 pt after the header (5 pt), 8–10 pt between entries (9 pt), 2–4 pt between bullets (3.15 pt) — and the bullet value **must be additive on top of line spacing**, otherwise bullets end up visually closer than the wrapped lines of a single bullet. — https://www.infiniteresume.com/blog/resume-formatting-standards-guide
- **A second, independent spacing set that converges:** 6–12 pt above section headings, 0–4 pt between bullets, body line spacing 1.0–1.15, body 10–12 pt, headings 13–16 pt, name 18–24 pt, margins 1 in (0.75 in when tight). — https://resume.io/blog/resume-spacing
- **The same source quantifies the reader:** 24% of hiring managers spend **under 30 seconds** on a resume. First-pass scan behavior, not deep reading, is the design target. — https://resume.io/blog/resume-spacing
- **A third spacing source, slightly looser:** 12–16 pt between sections, 6–10 pt between jobs, no extra gap between bullets; hierarchy order is name > headings > job titles > body > contact. — https://www.resumefast.io/blog/resume-formatting-guide
- **Typography discipline:** maximum two typefaces per resume, sans for headings / serif for body, avoid mixing emphasis styles (bold + italic + underline in one line). — Purdue OWL, https://owl.purdue.edu/owl/job_search_writing/resumes_and_vitas/resume_design.html
- **One family in 2–3 weights beats two families for a generated system.** Hierarchy via size, weight and space; a single accent color, never a palette. — https://madegooddesigns.com/resume-design-principles
- **100% of the "exotic font breaks ATS" fear is unsupported by measurement.** 14 px is the ideal body size, 12 px the floor, and 75–85 characters per line the readable measure. — https://learn.standardresume.co/design/visual-design
- **Line-length is a concrete layout constraint the engine must enforce:** 75–85 characters per line. At 11 pt on A4 with 0.75 in margins you get roughly 95–100 characters, i.e. a full-width single column is *too wide* — the engine should either narrow the text block (~6.3 in) or accept the upper bound deliberately. — https://learn.standardresume.co/design/visual-design
- **Length rule that is consistent across all 2026 sources:** 1 page under ~7–10 years, 2 pages for senior/staff/principal, and **the third page gets skipped**. — https://standout.work/blog/how-to-write-a-software-engineer-resume-in-2026
- **Two independent confirmations of the same threshold:** 1 page under 10 years / 2 after (https://novoresume.com/resources/resume-examples/software-engineer); 1 page to ~8 years, 2 after **only if page 2 is as dense as page 1** (https://resumematcher.fyi/blog/software-engineer-resume).
- **Recruiter expectations in numbers:** 64% expect 1–2 pages; 52% say candidates should quantify impact; 76% want organic relevance to the posting rather than keyword padding. — https://standout.work/blog/how-to-write-a-software-engineer-resume-in-2026
- **Applicant volume sets the bar for scannability:** a cold engineering posting draws **1,500–2,000 applicants**, which is why the first 30 seconds and the top third of page 1 carry almost all the decision weight. — https://standout.work/blog/how-to-write-a-software-engineer-resume-in-2026
- **Skills block:** 10–16 items, grouped, mirrored honestly from the posting, no skill bars, no white/hidden text. — https://standout.work/blog/how-to-write-a-software-engineer-resume-in-2026 ; https://thita.ai/blog/resume/best-resume-format-for-software-engineers-in-2026-ats-recruiter-friendly
- **Bullet grammar that survives both readers:** action verb + what was built + how (the technology) + measurable impact. — https://thita.ai/blog/resume/best-resume-format-for-software-engineers-in-2026-ats-recruiter-friendly
- **Contact block placement is a design *and* parsing decision:** name as plain text on line 1 at 14–18 pt, contact as ordinary body text on lines 2–3 — never in the page header region. — https://atsverification.com/blog/greenhouse-vs-workday-ats-parsing/
- **The one-minute layout self-test any engine can emulate:** select all, paste into a plain-text editor; if the order is wrong there, the layout is broken. — https://resumematcher.fyi/blog/software-engineer-resume
- **UNVERIFIED:** the widely repeated "6 seconds per resume" figure traces to low-quality secondary sources (e.g. https://eures.europa.eu/five-design-tips-your-resume-2019-12-13_en, 2019). The better-sourced 2026 framing is two-phase: **6–8 seconds** for the first scan, then **17–46 seconds** if the candidate passes — https://rezoom.io/how-long-do-recruiters-look-at-a-resume/ — but that page cites secondary sources and presents no primary measurement. Use it as a design prior, not a fact.

## Round B — ATS parsing reality, 2026

### FINDINGS — what actually fails, measured

- **The largest real-resume benchmark found:** 462 real resumes through production parsers. **4.5% produced no usable candidate record at all.** Failure rates by field: work experience 26.2% (17.1% judged likely-fail), no cleanly extractable name 10.2%, no email 4.3%, no phone 6.5%, **multi-column/table artifacts 25.8%** (14.1% likely-fail), section detection 16.7%, icons/graphics 10.2%, headers/footers 9.1%, dates 7.1%, skills 1.7%, education 1.1%. Across 1,085 separate analyses, **12.5% scored below 70** on a blended ATS score. — https://resumeatlas.io/ats-resume-parsing-benchmark
- **The failure hierarchy is structural, not cosmetic.** Layout (26.2%) and multi-column artifacts (25.8%) dominate; content-level fields (skills 1.7%, education 1.1%) barely fail at all. Design choices are the risk surface. — same URL
- **Controlled experiment, 108 generated PDFs, one variable at a time** (the strongest causal evidence found):
  - Word recovery: single column 100%, decorative bullets 100%, contact-in-margins 100%, no-space-characters 99.8%, **two columns 97.9%**, table grid 97.6%, **letter-spaced headings 96.9%**, **scanned image 0%**.
  - **Reading-order fidelity: single column 100%, table grid 93.4%, two columns 83.6%, two columns with narrow gutter 83%.**
  - **Line welding** (share of output lines fused from two unrelated source lines): **two columns 30.5%, narrow-gutter two columns 33.1%, table grid 24.1%, all eight other conditions 0%.**
  - Verbatim wreckage from the two-column condition: `SKILLS - Cut median checkout latency from 840ms to 210ms by reshaping the` and `555-0142 - Migrated 47 services...` — a phone number welded to an achievement. — https://atsprep.com/blog/resume-pdf-extraction-study
- **Letter-spacing is the single most under-reported failure mode.** Both tracked conditions scored 96.9% word recovery and the loss was *entirely* in headings: `E X P E R I E N C E`, `S K I L L S`, `E D U C A T I O N`. Because section headings are exactly what a parser uses to segment the document, this is not losing one word — it is losing the document's structure. — https://atsprep.com/blog/resume-pdf-extraction-study
- **The mechanism, stated numerically** (this is what makes it implementable rather than folklore): an extractor groups fragments within **2.5 pt of vertical distance** into one line, and inserts a space when the horizontal gap exceeds **the greater of 1.1 pt and 0.22 × character height**. At 11 pt body the threshold is ~2.4 pt; at 16 pt heading it is ~3.5 pt. Tracking of 1.5 pt and 2 pt pushed every inter-character gap over the threshold; 0.4 pt and 1 pt did not. — https://atsprep.com/blog/how-pdf-text-extraction-works
- **Counter-intuitive but measured:** a document containing **zero space characters** still recovered **99.8%** of words and 99.8% reading order, because word boundaries are rebuilt from geometry. Space characters are not what the parser looks for — distances are. — https://atsprep.com/blog/how-pdf-text-extraction-works
- **Three fears that measured as zero damage:** tight leading at 2 pt (100% / 100% / 0% welded), symbol-font bullets (100% / 100% / 0%), rotated sidebar (100% / 100% / 0%). Do not spend engine effort on bullet glyph choice or tight leading. — https://atsprep.com/blog/resume-pdf-extraction-study
- **Contact in page margins loses nothing but moves everything:** 100% word recovery, only **93.7% order fidelity**, with email and phone returning at the far end of the text, far from the name. — same URL

### FINDINGS — platform-specific rules

- **Workday (official vendor documentation, the only first-party spec found):** DOCX or text-based PDF only; do **not** put personal information in header/footer; no images, text boxes or logos; no tables or columns; **separate section headings — never a combined "EDUCATION and EXPERIENCE"**; one role per block; 4-digit years; a `Name: Xxxx Yyyy` hint improves name detection; **Skills and Languages are not auto-populated by parsing** at all. — https://developer.workday.com/documentation/GUID-f07adb7f-630e-42a2-9de9-a39652e34ec5-enHYPHENus/ResumeRESTAPI ; https://doc.workday.com/admin-guide/en-us/human-capital-management/recruiting/candidates/set-up-prospects-and-candidates/hdc1552497830785.html
- **Greenhouse:** resumes **larger than 2.5 MB cannot be parsed** — a hard, checkable ceiling the build pipeline should assert. — https://support.greenhouse.io/hc/en-us/articles/200989175-Unsuccessful-resume-parse
- **Lever:** parses DOCX, PDF, RTF, WordPerfect, HTML, ODF; cannot parse images; the vendor's own test is "can you highlight the text?" — https://help.lever.co/s/article/Understanding-Resume-Parsing
- **Format defaults per portal (2026 practitioner guidance):** DOCX/Word-originated documents default-safest on Workday and Taleo; text-based PDF for postings that request PDF, USAJOBS, and email; **PDF exported from a design tool is the low-reliability case**, not PDF as such. — https://hireflow.net/blog/what-file-format-should-my-resume-be-in-2026
- **Two-column verdict from a 15-layout extraction test** (pdf.js, pdftotext default, pdftotext -layout, mammoth): the single column was the **only** arrangement that came out identical in all four tools. The same two-column file was merely reordered in one tool and cut mid-sentence in another. A **right** sidebar pushed contact details to *after* education; a **left** sidebar pushed them *before* the summary. Contact in the Word page header was **missing entirely** from mammoth output. — https://www.cvmakeover.ai/en/blog/two-column-resume
- **A second 21-template test agrees and adds the honest caveat:** pdf.js extraction is an approximation of a parser, not a vendor ATS; the study checked order, overlap and margins, **not whether text was lost**. — https://applycove.com/blog/two-column-resume-ats
- **Why columns break, mechanically:** a PDF stores positioned glyphs, not paragraphs; there is no column object. Extractors either follow content-stream order or rebuild from geometry, and the two disagree. W3C's accessibility guidance makes the identical point about untagged multi-column documents — a screen reader reads "top to bottom, across both columns". Swap "screen reader" for "resume parser" and the whole column problem is stated. — https://www.resumecommand.com/resources/resume-tips/two-column-resume-ats
- **The contrarian position, worth recording because it is partly right:** fonts, color, and a two-column layout built from a *real* table generally do not break parsing; the industry repeats myths. — https://reach.jobs/guides/ats-myths-resume-parsing-facts . The measurement above reconciles this: the words survive (97.9%), the **order** does not (83.6%), and ordering is what field-mapping depends on.
- **Myth correction with numbers:** **92% of ATS platforms do not auto-reject on design grounds** (Enhancv 2025, via secondary citation) — https://resumeoptimizerpro.com/blog/do-you-need-a-cover-letter-2026 . Separately, **88% of employers agree that qualified high-skill candidates are screened out** by their own automated filters — Harvard Business School + Accenture, *Hidden Workers* (2021) — https://sapia.ai/resources/blog/resume-parsing-software . Both are true at once: design is rarely an instant reject, but it silently degrades match quality.

### FINDINGS — keywords and tailoring

- **Tailoring beats everything else, quantified:** scanning against a specific job description improves average score by **22 points** versus a generic scan, across an opt-in sample of **2,417 of 8,902 scans (27.2% opt-in)**. Software Engineering was the largest role bucket: **N=687, average score 64**. — https://www.atschecker.ai/research/ats-resume-study-2026 (vendor-published, disclosed, aggregate-only)
- **The 64/100 software-engineering average is the most useful single calibration point found:** a well-built engineer resume lands mid-60s against a real JD. A generator should target reproducible improvement over *baseline for this candidate*, not an absolute 90+.
- **Keyword stuffing has no measured upside and two measured downsides:** invisible/white text is flagged by every mainstream checker, and skill bars / circular ratings / flags / logos "consume space, create uncertain reading order, and often communicate less than a short phrase". — https://latex2svg.com/blog/ats-friendly-resume-latex
- **Mirror the posting's vocabulary honestly.** Terms must appear in full sentences inside the extractable flow; keywords in footers or bullet grids may never enter the text stream. — https://hireflow.net/blog/cover-letter-formatting-for-ats

## Round C — LaTeX specifics (the engine's riskiest surface)

### FINDINGS

- **Trap #1 is ligatures, and the standard fix is an encoding fix, not a ligature fix.** fi/fl/ff/ffi can extract as a single glyph when no ToUnicode map exists. For pdfLaTeX: `\usepackage[T1]{fontenc}` + `lmodern` + `cmap`; belt-and-braces `\usepackage{microtype}\DisableLigatures{encoding = *, family = *}`; for XeLaTeX/LuaLaTeX: `\setmainfont{YourFont}[Ligatures=NoCommon]`. Verify with `pdftotext resume.pdf - | head -40`. — https://atsverification.com/blog/latex-resume-ats-friendly
- **A measured contradiction of the usual advice, which changes the fix:** in a 15-document pdfLaTeX bench on TeX Live 2026, **ligatures extracted as plain letters in every variant, with or without the glyphtounicode line**, because the format already sets `\pdfgentounicode=1` and every font carried a ToUnicode map. The real breakage was the **encoding**: with default **OT1**, `ü` came out as `u` + U+0308 (combining diaeresis) from pdftotext and as **U+00A8 + space** from pypdf, i.e. `Zo¨ e M¨ uller,´Ecole Polytechnique, Z¨ urich`. With **T1**, both tools returned a single U+00FC. — https://latexci.com/latex-resume-ats
- **So the engine must set T1 unconditionally, and keep the glyphtounicode line as cheap insurance** for installations that do not pre-set it. Both are one line each; neither is optional-by-taste. — same URL
- **`\pdfinterwordspaceon` fixes label-gluing.** pdfTeX does not write space characters — it moves the next word right. pypdf therefore returned `SkillsPython, SQL, Spark, Airflow` when a bold label was followed by `\quad`. Writing real spaces with `\pdfinterwordspaceon` produced `Skills Python, SQL, Spark, Airflow`. **This is a one-line fix for the single most common LaTeX-resume extraction defect.** — https://latexci.com/latex-resume-ats
- **Icon fonts are a confirmed, reproduced failure.** With `fontawesome5`, pdftotext returned `# jane.doe@example.com`, `[U+0083] +33 6 12 34 56 78`, `ï in/janedoe`, `§ janedoe`; pypdf returned `/envel⌢pejane.doe@example.com♂phone+33...`. With the same line written as labels (`Email:`, `Phone:`, `LinkedIn:`, `GitHub:`) both extractors returned clean text. — https://latexci.com/latex-resume-ats
- **`\quad` separators can also reorder the line** — a wide gap made pdftotext read a wrapped contact line as columns and emit "GitHub" second. Use a **visible separator** (a vertical bar) instead of wide spacing. — same URL
- **Date placement, tested five ways against three readings** (this is the table to implement from):

  | Layout | pdftotext | pdftotext -layout | pypdf |
  |---|---|---|---|
  | Date column via `tabular` | kept | kept | **glued to the title** |
  | Same + `\pdfinterwordspaceon` | kept | kept | kept |
  | Date column via two `minipage` | **separated** | **separated** | **separated** |
  | Title line, date pushed right with `\hfill` | **separated** | kept | kept |
  | Title line, date after a comma | kept | kept | kept |

  Only two layouts kept every date attached in all three readings: **date after the title comma**, and **tabular + `\pdfinterwordspaceon`**. A `minipage` date column lost the date in *every* reading by emitting `2021–2024 / 2019–2021` *before* both jobs. — https://latexci.com/latex-resume-ats
- **`\hfill` right-aligned dates are a latent layout hazard**: pdftotext default mode pushed the date **below** the bullet lines. This is the classic "moderncv classic" geometry and it is exactly why that style is rated riskier than `banking`. — same URL
- **PDF metadata is a checklist item, not decoration.** `\usepackage[hidelinks,pdfusetitle]{hyperref}` plus `\hypersetup{pdftitle={Jane Doe, CV}, pdfauthor={Jane Doe}, pdflang={en}}` produces `Title:` and `Author:` in `pdfinfo`. Whether any ATS reads PDF metadata is **UNVERIFIED**; it is cheap, it helps humans and portals that show a filename fallback, and it costs one line. — https://latexci.com/latex-resume-ats
- **Template risk tiers with live GitHub stars (Oct 2026), as a build decision rather than a taste decision:**
  - **Jake's Resume** — 2,829★, MIT, **Low** risk (single column, `glyphtounicode`).
  - **sb2nov/resume** — 7,048★, MIT, **Low** (same technique, `\input{glyphtounicode}` + `\pdfgentounicode=1`).
  - **Awesome-CV** — 28,729★, LPPL 1.3c, **Low–Medium** (icon header; now requires **LuaLaTeX + HarfBuzz + fontawesome6** via `latexmk`; XeLaTeX/pdfLaTeX unsupported).
  - **moderncv** — ~1,000★, LPPL 1.3c, **Medium** (dates in a left column; `banking` style is the single-column ATS-safe variant, `classic` is not).
  - **AltaCV** — 1,583★, LPPL, **High** (paracol two-column).
  - **Deedy** — 5,065★, Apache 2.0, **High** (two asymmetric columns).
  — https://www.atsresumeai.com/blog/best-overleaf-resume-templates ; https://www.useoctree.com/blog/latex-resume-templates-professional-cv-guide ; https://github.com/posquit0/Awesome-CV
- **moderncv is separately flagged as "Tagged PDF – incompatible" (v2.6.1, 2026-06-24)**, while LaTeX News 42 (Nov 2025) reports tagged/accessible PDF as production-ready for supported packages. Accessibility tagging and ATS extraction are different goals but both favour the same thing: real structure, one flow. — https://resufit.com/fr/blog/guide-complet-des-modeles-cv-latex-excellence-professionnelle-et-academique
- **fontspec defaults matter for a LuaLaTeX build:** `Ligatures=TeX` is **on by default**; `NoCommon` disables `liga` (measured: `fi` advance 6.05 pt → 6.35 pt, i.e. disabling ligatures widens the pair). The global form is `\defaultfontfeatures{Ligatures={NoCommon,NoRequired,NoContextual,NoHistoric,NoDiscretionary}}`. — https://tex64.com/learn/fonts/fontspec ; http://latex3.github.io/fontspec/fontspec.pdf ; https://texfaq.org/FAQ-prevlig
- **microtype is safe *and* is the wrong place to get "polish".** Default load is `\usepackage{microtype}` (protrusion on, expansion on where the font supports it); it **changes line and page breaks**, so expect reflow. Critically: **letterspacing/tracking is a microtype feature and is exactly what shreds headings** — so the engine loads microtype for protrusion/expansion and sets **tracking to zero everywhere**. — https://ctan.math.illinois.edu/macros/latex/contrib/microtype/microtype.pdf ; https://casrai.org/guides/latex-microtype
- **microtype's engine support is uneven** — protrusion and letterspacing work in XeTeX; **font expansion, ligature disabling, interword spacing and kerning do not**. So a XeLaTeX build gets less microtype, and `\DisableLigatures` needs `fontspec` instead. — https://casrai.org/guides/latex-microtype
- **A production-ready minimal ATS preamble found in the wild** (10 pt article, T1, lmodern, 0.68 in geometry, microtype, enumitem, hidelinks): `\setlist[itemize]{leftmargin=1.25em,itemsep=2pt,topsep=3pt}` and a section macro of `\vspace{8pt}` + `\large\bfseries` + `\vspace{2pt}` + `\hrule` + `\vspace{4pt}`. Note the tension with Round A's 12–16 pt: 8 pt above + 2 pt below is *tight*; the engine should use ~10–12 pt above and 4–5 pt below. — https://latex2svg.com/blog/ats-friendly-resume-latex
- **Explicit anti-pattern list from a build tool:** no absolute positioning, no custom drawing packages, no skill bars, no circular ratings, no flags, no headshots, no QR codes, no color-only categories, no hidden keywords. — same URL
- **The verification ritual the engine should automate:** `pdftotext -layout resume.pdf out.txt`, read top to bottom; `pdffonts resume.pdf` to confirm embedded fonts and encoding; `pdfinfo resume.pdf` for metadata. — https://latex2svg.com/blog/ats-friendly-resume-latex

## Round D — Cover letter, 2026

### FINDINGS — does it matter

- **The only field experiment in the literature (and its exact numbers):** ResumeGo sent **7,287** fictitious applications to live postings between 2019-07-15 and 2020-01-10. 30-day callback rates: **no letter 10.7%, generic letter 12.5%, tailored letter 16.4%** — the widely quoted "+53%" is a *relative* lift from 10.7% to 16.4%, i.e. **+5.7 percentage points absolute**. A generic letter is only **+1.8 points**, so roughly **two thirds of the entire benefit comes from tailoring, not from attaching a document**. — https://www.resumego.net/research/cover-letters ; arithmetic and caveats: https://www.careerpigeon.ai/blog/do-recruiters-read-cover-letters
- **Honest boundary on that study, stated by the sources that cite it:** it was run by a company that sells cover-letter writing; no per-arm sample size, no significance test published; it predates widespread AI drafting. One study, unreplicated. — https://www.careerpigeon.ai/blog/do-recruiters-read-cover-letters ; https://resumeproofed.com/blog/do-you-need-a-cover-letter
- **Readership is genuinely contested and the surveys conflict in a way worth knowing:** ResumeGo's survey of 236 recruiters/hiring managers found **87% read cover letters, 65% say letters materially influence decisions, 81% value tailored over generic, 78% say generic is easy to spot, and 76% do not reject solely for a weak letter** (https://www.resumego.net/research/cover-letters) — while a **2024 ResumeBuilder survey of 948 US hiring managers** found only **26% always or frequently read them and 44% never do** (via https://resumeproofed.com/blog/do-you-need-a-cover-letter). The synthesis both sources converge on: letters are read closely when the resume raises a question (career change, gap, unusual mix), at small companies, for senior roles, and after a referral.
- **Circulating statistics that do not survive citation tracing:** the "91% of executives" figure attributed to Robert Half 2026 is a **February 2012 OfficeTeam survey**, and it found executives called cover letters *valuable* — not that they include them. The "84%" figure appears in no primary source. — https://www.careerpigeon.ai/blog/do-recruiters-read-cover-letters
- **AI-detection risk is real and asymmetric:** **19.6%** of hiring managers say they would reject an AI-generated cover letter or resume (TopResume, N=600, 2025); a 2025 survey reports **88%** claim they can detect AI-written content. — https://asktherecruiter.com/blog/tips-for-cover-letters-to-get-more-interviews/ ; https://applygoat.com/blogs/cover-letter-statistics-2026 . Both are opinion surveys. Treat as: the letter must contain specifics no generic generator could produce.
- **Length preference is consistent:** **~70% of employers want a half-page letter or as short as possible**, **76% prefer half a page or less**, and the recommended range is **250–400 words / three to four short paragraphs**. Recruiters spend **30–60 seconds** scanning one. — https://applygoat.com/blogs/cover-letter-statistics-2026 ; https://nz.seek.com/career-advice/article/how-long-should-a-cover-letter-be (250–400 words, one page, 3–6 paragraphs)

### FINDINGS — ATS handling and format

- **What actually happens on upload:** the resume is mapped into profile fields; **the letter rides alongside** — into a Documents tab, a dedicated upload slot, or a free-text area. Some tenants keyword-match the inline text; attachments are often stored unranked. **No major vendor documents that cover letters feed a ranking score.** — https://hireflow.net/blog/how-ats-processes-cover-letters ; https://atsverification.com/blog/do-ats-read-cover-letters-workday-greenhouse-lever-tested
- **Vendor confirmation of the negative:** "We found no Greenhouse statement that cover letters are parsed… They say only that candidates can upload resumes and cover letters as .doc, .docx, .pdf, .rtf or .txt." — https://www.atshiring.com/en/learn/ats-cover-letter-guide-how-to-write-ats-friendly-cover-letter-2025
- **Format rules are identical to the resume's, and for the same mechanical reasons** — one column, standard font 11–12 pt, contact in body text (not header/footer), no tables/text boxes/logos/icons, text-based PDF or DOCX, one page. — https://hireflow.net/blog/cover-letter-formatting-for-ats
- **Format reliability ranking (practitioner, 2026):** `.docx` highest; `.pdf` exported from Word high; **`.pdf` exported from a design tool low — "text may not extract at all"**; `.txt` and pasted-into-form perfect. — https://cvpilot.pro/blog/ats-friendly-cover-letter-2026-uk-guide
- **Structure that both parsers and humans skim cleanly:** date line, employer block, salutation, **three short paragraphs**, close — with the exact job title in the first paragraph and 3 posted keywords in full sentences (not a list). — https://hireflow.net/blog/cover-letter-formatting-for-ats
- **Four-part variant used by a production ATS guide:** hook → value → proof → close, **250–400 words, 4–6 JD keywords in natural sentences**. — https://www.atshiring.com/en/learn/ats-cover-letter-guide-how-to-write-ats-friendly-cover-letter-2025
- **If only one upload slot exists:** letter as page 1, resume as page 2+, one text-based PDF; **keep the letter ≤250–350 words** because the parser now sees prose before structure. — https://applygoat.com/blogs/cover-letter-upload-fields-that-only-accept-one-file-in-2026-combining-resume-letter
- **Never:** "To Whom It May Concern". Use a named manager, else "Dear [Company] Recruiting Team". — https://careerquiver.com/blog/do-ats-systems-read-cover-letters/
- **Contact digits must match the resume exactly** — mismatched phone/email between the two documents is a cheap, self-inflicted profile-merge failure. — https://hireflow.net/blog/how-us-ats-processes-cover-letters-what-it-extracts

## Round E — Measurement: length, format, naming, verification

### FINDINGS

- **Length:** senior/staff = **2 pages**; page 3 is skipped. Under ~7–10 years = 1 page. **64% of recruiters expect 1–2 pages.** — https://standout.work/blog/how-to-write-a-software-engineer-resume-in-2026
- **Date format:** `MM/YYYY` plus "Present" for the current role. — https://novoresume.com/resources/resume-examples/software-engineer
- **PDF vs DOCX — there is no universal winner, and the decision rule is short:** follow an explicit instruction; if both are accepted, a **verified text-layer PDF** is a reasonable default for layout stability; use DOCX when a legacy portal warns about PDF. **The construction of the file matters more than the extension.** — https://atsprep.com/blog/pdf-vs-docx-for-ats
- **DOCX's advantage is structural, not aesthetic:** DOCX stores paragraphs, lists and real heading styles that compatible software can read directly — provided the file is built from ordinary paragraphs and list styles rather than tables, text boxes, frames, and manual spacing. — same URL
- **Portal-specific format defaults (practitioner, 2026):** default to a simple single-column **DOCX from Word or Google Docs** when the portal accepts it, *especially Workday and Taleo*; keep a text-based PDF for postings that request PDF or for email. — https://hireflow.net/blog/what-file-format-should-my-resume-be-in-2026
- **File naming — two conventions, both fine, both specific:**
  - `Firstname_Lastname_Resume.pdf`, add a short role keyword when running multiple versions (`Daniel_Okafor_ProductManager_Resume.pdf`), cover letters get `Firstname_Lastname_CoverLetter_Company.pdf`; hyphens stay hyphens in double-barrelled names; **skip `final`/`v3`**. — https://hireflow.net/blog/best-resume-file-name-and-what-to-avoid
  - `Jane-Doe-Software-Engineer-Resume.pdf` / `FirstName-LastName-Role-Resume.docx`. — https://www.joinleland.com/library/a/how-to-craft-an-effective-software-engineering-resume ; https://hireflow.net/blog/workday-resume-format-2026
- **Filename indexing by ATS is plausible but UNVERIFIED** — one source asserts "some systems index the filename" without a citation: https://cvpilot.pro/blog/ats-friendly-cover-letter-2026-uk-guide . The human benefit (never sending the wrong file) is sufficient justification on its own.
- **The extractor constants that turn "ATS-friendly" into assertions** — implement these as the engine's test thresholds: line grouping **2.5 pt**; word-boundary insertion when horizontal gap > **max(1.1 pt, 0.22 × char height)**; at 11 pt the threshold is ~2.4 pt, at 16 pt ~3.5 pt. — https://atsprep.com/blog/how-pdf-text-extraction-works
- **Acceptance bands from the 108-document corpus:** a conforming single-column document should score **100% word recovery, 100% reading-order fidelity, 0% welded lines**. Two-column and table-grid layouts score 97.9/83.6/30.5 and 97.6/93.4/24.1 respectively — so a regression test can distinguish "conforming" from "shipping a sidebar" numerically rather than by eye. — https://atsprep.com/blog/resume-pdf-extraction-study
- **A candidate-level calibration figure:** software-engineering resumes average **64/100** against a real posting (N=687); tailoring adds **+22 points** on average (N=2,417). — https://www.atschecker.ai/research/ats-resume-study-2026
- **No credible callback-rate delta attributable to resume *formatting* was found.** The ResumeGo numbers measure cover-letter presence/tailoring, not resume design. **UNVERIFIED** — do not claim one.
- **Scan-time figures remain weakly sourced** — 6–8 s first scan / 17–46 s if passing (https://rezoom.io/how-long-do-recruiters-look-at-a-resume/), 24% under 30 s (https://resume.io/blog/resume-spacing). Directionally consistent, no primary measurement. Use for prioritisation, not for a claim.

## DECISIONS FOR THIS ENGINE

Concrete rules, derived from the measurements above. Each is implementable as code or as a test.

### 1. Layout: one column, always

- **Single text flow. No sidebars, no `minipage` pairs, no `paracol`, no `tabular` for layout, no CSS grid/flex for the resume body, no DOCX text frames or floating tables.** Rationale: welding 30.5% (two-col) / 33.1% (narrow gutter) vs 0% (single column); reading order 100% vs 83.6%.
- **Dates go on the title line, after a comma** (`Data Engineer, Acme Analytics, 2021–2024`). Never `\hfill`-right-aligned (pdftotext pushes them below the bullets), never a `minipage` date column (emitted before both jobs in all three readings), never a bare `tabular` column without `\pdfinterwordspaceon`.
- **Contact details live in the body, lines 2–3**, never in the LaTeX page header, the DOCX header region, or the page margin box. Rationale: header content was missing entirely from one Word extractor; margin contact lost 6.3 points of order fidelity.
- **Reading order == DOM order == source order** in all three backends. If the HTML uses CSS for any visual grouping, the template must still emit blocks in reading sequence.

### 2. Type scale and spacing (the numbers)

```yaml
page:      A4 or Letter, margins 0.75in (0.7in when content-tight)
name:      20pt bold, plain text, line 1         # 18–24 band
contact:   10.5pt, lines 2–3, visible "|" separators (never \quad)
section:   11.5pt bold, ALL CAPS-or-smallcaps, tracking = 0
job title: 11pt bold
dates:     10.5pt regular, on the title line, after a comma
body:      10.5pt (never <10pt)                  # 10–12 band
leading:   13.5pt baseline (≈1.29 × body)
measure:   75–85 characters per line → cap text block at ~6.3in on A4
accent:    one color only (headings rule + links), never a palette
fonts:     one family, 2–3 weights; sans for headings, serif optional for body
spacing:
  before_section: 12pt
  after_section_rule: 5pt
  between_entries: 9pt
  between_bullets: 3pt ADDITIVE on top of leading   # not a replacement
```

- Section header rendering: `\vspace{12pt}` + bold/smallcaps + hairline rule + `\vspace{5pt}`. **No tracking.** Same in CSS: `letter-spacing: 0`.

### 3. Section order (senior SWE, 17 yrs, AI/LLM + mobile)

1. **Name + contact** (no "Curriculum Vitae" label, no photo, no logo)
2. **Summary** — 2–3 lines max, one sentence on scope/years, one on domain (AI/LLM + mobile), one on a hard, dated outcome
3. **Skills** — 3–5 groups, 10–16 items total, plain comma lists, no bars, no ratings, no flags
4. **Experience** — reverse chronological, one role per block, 4-digit years, 4–6 bullets for the last two roles and 2–3 for older ones
5. **Selected Projects / Open Source** — only if it carries evidence the experience block cannot
6. **Education** — separate heading, never merged with Experience
7. **Publications / Patents / Talks** — optional, senior-IC relevant
8. **Not included:** References, "Interests" filler, skill bars, availability statements

- **Workday requires separate section headings** — never a combined "EDUCATION and EXPERIENCE" heading; one role per block; 4-digit years throughout.
- **Bullet grammar, enforced by prompt:** `Verb + object built + how (technology) + measurable outcome`. 52% of recruiters say candidates should quantify; the generator must refuse a bullet with no number unless the user explicitly marks it unquantifiable.

### 4. LaTeX preamble — non-negotiable lines

```latex
\documentclass[10.5pt]{article}          % or extarticle for 10.5
\usepackage[T1]{fontenc}                 % MANDATORY — OT1 mangles accents
\usepackage{lmodern}                     % or the licensed family + T1
\usepackage[sfdefault]{...}              % optional
\input{glyphtounicode}\pdfgentounicode=1 % cheap insurance
\pdfinterwordspaceon                     % MANDATORY — stops label gluing
\usepackage[protrusion=true,expansion=true]{microtype}
\DisableLigatures{encoding = *, family = *}
\usepackage[margin=0.75in]{geometry}
\usepackage{enumitem}
\setlist[itemize]{leftmargin=1.25em,itemsep=3pt,topsep=3pt,parsep=0pt}
\usepackage[hidelinks,pdfusetitle]{hyperref}
\hypersetup{pdftitle={<Name> — CV}, pdfauthor={<Name>}, pdflang={en}}
\pagestyle{empty}\pagenumbering{gobble}
\setlength{\parindent}{0pt}
```

- **Tracking/tracking-zero rule:** never `\textls`, `\lsstyle`, `\SetTracking`, or `\so` on headings. Round B measured that 1.5 pt and 2 pt tracking shreds headings into `E X P E R I E N C E`; 0.4 pt and 1 pt were safe — but "safe at 0.4 pt" is a tolerance, not a licence. Set 0.
- **XeLaTeX/LuaLaTeX variant:** `\defaultfontfeatures{Ligatures={NoCommon}}` and `\setmainfont{...}[Ligatures=NoCommon]`; accept the loss of microtype's expansion/ligature features under XeTeX.
- **Do not build on moderncv (classic), AltaCV, or Deedy.** If a template look is required, use a Jake's-Resume-shaped structure (single column, MIT) or sb2nov's, both rated Low risk.

### 5. Hard bans (each maps to a measured failure)

| Ban | Evidence |
|---|---|
| Two columns / sidebar / `paracol` / `minipage` pairs | 30.5–33.1% welded lines, 83–83.6% order fidelity |
| `\hfill` right-aligned dates | date pushed below bullets in pdftotext default mode |
| `minipage` date column | date emitted before both jobs in all 3 readings |
| Letter-spacing / tracking on headings | headings return as `E X P E R I C E N C E`-style letter runs; 96.9% word recovery |
| Icon fonts (fontawesome) for contact | `[U+0083]`, `ï`, `§`, `/envel⌢pe` in extracted text |
| `\quad`-separated contact items | can reorder the line; use a visible `\|` |
| Tables used for layout | 24.1% welded lines, 93.4% order |
| Scanned / image-only PDF; PDF from a design tool | 0% recovery (the only total failure measured) |
| Header/footer contact details | missing entirely in one Word extractor; 9.1% header/footer failure rate on real resumes |
| Multi-column DOCX, text boxes, floating tables | 4.5% of real resumes produce no usable record |
| Skill bars, circular ratings, flags, photos, QR codes, logos | no parsing value; "create uncertain reading order" |
| White/hidden/tiny text for keywords | deceptive, flagged by checkers |
| Resume > 2.5 MB | Greenhouse refuses to parse |

### 6. DOCX and HTML backends

- **DOCX:** real Word paragraph styles (`Heading 1` named literally `EXPERIENCE`, `EDUCATION`, `SKILLS`), ordinary paragraphs and list styles, **no tables for layout, no text frames, no floating shapes, no header/footer content**. Fonts restricted to a safe set (Calibri, Arial, Georgia, Times New Roman) at 10.5–11 pt. Identical wording to the PDF — one source of truth, generated together, or drift produces a stale phone number in one file.
- **HTML:** semantic single-column flow (`h1`, `h2`, `p`, `ul`), `letter-spacing: 0` on all uppercase headings, no icon fonts (text labels only), print stylesheet with `@page { margin: 0.75in }`, and DOM order == reading order. This HTML is also the cheapest place to run the paste-test assertions.

### 7. Cover letter — skeleton and rules

- **Default: write one, tailored. Do not send a generic letter.** Numbers: tailored 16.4% callback vs no letter 10.7% (+5.7 pp); generic 12.5% (+1.8 pp). Two thirds of the benefit is tailoring.
- **Skip when:** a quick-apply form with no upload field or text area, or when nothing specific can honestly be said.
- **Length:** 250–350 words, ≤1 page, **4 blocks**:

  ```
  [Name] · [City] · [Phone] · [Email]        ← identical digits to the resume
  [Month D, YYYY]

  Dear <Name | Company> Recruiting Team,     ← never "To Whom It May Concern"

  ¶1  Role + company + the single strongest matching proof, 2–3 JD
      keywords in full sentences.
  ¶2  One specific piece of evidence the resume cannot carry: a system,
      a scale, a number, a decision and its outcome.
  ¶3  Why this company/team, concretely — no generic flattery.

  Sincerely,
  [Name]
  ```

- **Format:** DOCX by default; text-based PDF from Word-equivalent export if PDF is requested; **never a design-tool PDF**. One column, 11–12 pt, contact in body text, no logo header, no teal sidebar, no two-column contact block.
- **If one upload slot only:** letter page 1, resume page 2+, single PDF, keep the letter ≤250–350 words.
- **AI-detection mitigation:** every paragraph must contain a fact that could not survive a company swap — a named system, a number, a specific team or product. This is a content rule, and it also happens to be the tailoring that carries the 5.7 points.

### 8. File naming

```
<Firstname>-<Lastname>-<Role>-Resume.pdf      # canonical
<Firstname>-<Lastname>-<Role>-Resume.docx     # same stem, different extension
<Firstname>-<Lastname>-CoverLetter-<Company>.pdf
```

- Role token short: `Senior-SWE`, `AI-Engineer`, `Mobile-Lead`. No `final`, no `v3`, no req numbers. Hyphens preserved in double-barrelled surnames.

### 9. Build-time verification gates (fail the build, don't warn)

Run for every generated PDF. These turn the research into CI.

```
1. pdftotext -layout out.pdf -            → assert section headings each on their own line,
                                             in the intended order
2. assert NOT /^([A-Z] ){3,}[A-Z]$/m      → no shredded/letter-spaced heading
3. assert no PUA codepoints               → U+E000–U+F8FF, U+0083, 'ï', '§', '⌢'
4. assert name, email, phone in first 10 extracted lines
5. assert no line contains tokens from two different sections   (welding proxy:
   if a line has a phone/email fragment AND a bullet verb, fail)
6. assert dates adjacent to their job titles (regex: title line contains a 4-digit year
   or "Present" within the same line or the immediately following line)
7. assert word count and page count (senior: 2 pages max)
8. assert file size < 2.5 MB              (Greenhouse ceiling)
9. pdfinfo → assert Title and Author present
10. pdffonts → assert all fonts embedded, all with ToUnicode
11. assert contact digits in the PDF == contact digits in the DOCX == source of truth
12. keyword coverage: assert each of the top-N JD terms appears in a full sentence
    (target: reproduce the +22-point tailoring lift, not a raw score of 90)
```

- **Acceptance bands:** single-column documents should hit 100% word recovery / 100% order / 0% welding against the extractor model. Any generated CV that the harness scores below the table-grid band (97.6 / 93.4 / 24.1) is definitionally shipping a multi-region layout and should be rejected.
- **Do not chase a 90+ ATS score.** Software-engineering resumes average 64/100 against real postings; the honest target is a measured improvement over this candidate's own baseline with the JD in hand.

- Whether cover-letter text feeds any ranking score at Workday/Greenhouse/Lever. **Vendors do not publish it; no external tool can see it.**
- Whether ATS index filenames. **UNVERIFIED.**
- A callback-rate delta attributable to resume *design*. **No credible number exists.** The only field-experiment numbers concern cover-letter presence and tailoring.
- Per-platform parse failure rates for Taleo, iCIMS, Jobvite, SuccessFactors, Bullhorn, BambooHR individually. **UNVERIFIED** — only the aggregate 462-resume benchmark and the four platforms with first-party or well-sourced documentation are covered here.
